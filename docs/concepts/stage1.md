# 1단계 개념 노트

1단계에서 익힐 개념 5개. 각 개념은 비유 → 정의 → 실제 사례 → 확인 질문 순서다.
다 읽고 확인 질문에 막힘없이 답할 수 있으면, 비서에게 "하루 정리"를 요청해 개념 사전에 이해도를 기록하자.

---

## 1. 토큰 (Token)

**비유:** 레고 블록. 문장을 그대로 먹는 게 아니라, 잘게 쪼갠 블록 단위로 읽고 쓴다.

**정의:** LLM이 텍스트를 처리하는 최소 단위. 단어 하나일 수도, 단어의 일부일 수도, 문장 부호 하나일 수도 있다. 이 쪼개는 규칙을 **토크나이저**라고 한다.

**실제 사례:**
- 영어 "unbelievable"은 `un` + `believ` + `able`처럼 여러 토큰이 될 수 있다.
- 한국어는 대체로 같은 의미를 표현할 때 영어보다 토큰이 더 많이 든다.
- API 요금, 속도 제한, 최대 출력 길이(`max_tokens`)가 모두 토큰 단위다.

**확인 질문:**
- 같은 내용을 한국어와 영어로 보낼 때 비용이 다를 수 있는 이유는?
- `max_tokens`를 너무 작게 잡으면 어떤 일이 생기나?

---

## 2. 컨텍스트 윈도우 (Context Window)

**비유:** 책상 위 공간. 책상에 올려 둔 자료만 보면서 일할 수 있고, 책상 밖 자료는 없는 것과 같다.

**정의:** 모델이 한 번의 요청에서 볼 수 있는 토큰의 최대량. 시스템 프롬프트, 대화 기록, 첨부 문서, 도구 결과, 그리고 모델이 새로 쓰는 답까지 모두 이 안에 들어가야 한다.

**실제 사례:**
- 모델은 대화를 "기억"하는 게 아니라, 매 요청마다 지난 대화를 통째로 다시 받는다.
- 대화가 길어지면 오래된 내용을 요약(compaction)하거나 잘라 내야 한다.
- 그래서 이 비서는 오래 남길 정보를 Notion에 저장한다. 책상 밖 서랍인 셈이다.

**확인 질문:**
- 모델이 "지난주 대화를 기억한다"는 말은 기술적으로 어떻게 가능한가?
- RAG가 컨텍스트 윈도우 문제를 어떻게 덜어 주는지 한 문장으로 말해 보자. (3단계 예고)

## 3. 트랜스포머와 어텐션 (Transformer, Attention)

**비유:** 회의 중 메모하는 사람. 새 문장을 쓸 때마다 "지금 이 단어를 쓰려면 앞의 어떤 말들이 중요하지?"를 다시 훑어보고 가중치를 준다.

**정의:**
- **어텐션:** 각 토큰이 다른 모든 토큰을 보고, 지금 자신에게 얼마나 관련 있는지 점수를 매겨 정보를 섞는 계산.
- **트랜스포머:** 어텐션 층을 여러 겹 쌓은 신경망 구조. 오늘날 LLM 대부분의 뼈대다.
- LLM은 이 구조로 **다음 토큰 하나를 예측**하고, 그 결과를 다시 입력에 붙여 또 다음 토큰을 예측하는 일을 반복한다.

**실제 사례:**
- "철수는 영희에게 책을 줬다. 그녀는 고맙다고 했다."에서 '그녀'를 처리할 때 '영희'에 높은 어텐션이 걸린다.
- 모든 토큰이 모든 토큰을 보기 때문에, 입력이 길어질수록 계산량이 크게 늘어난다. 긴 컨텍스트가 비싼 이유다.

**확인 질문:**
- LLM이 긴 글을 "한 번에" 쓰는 게 아니라는 말은 무슨 뜻인가?
- 입력 길이가 두 배가 되면 어텐션 계산량은 대략 어떻게 변하나?

---

## 4. 샘플링 (Sampling)

**비유:** 메뉴 고르기. 모델은 다음 토큰 후보마다 확률을 매기고, 그중 하나를 고른다. 늘 1등만 고를 수도, 가끔 2~3등을 고를 수도 있다.

**정의:** 모델이 계산한 다음 토큰 확률 분포에서 실제 토큰 하나를 뽑는 방법.
- **temperature:** 높을수록 낮은 확률 후보도 자주 뽑아 다양해지고, 낮을수록 안정적이다.
- **top_p / top_k:** 후보를 상위 일부로 좁혀서 뽑는다.

**실제 사례:**
- 같은 질문을 두 번 해도 답이 조금씩 다른 이유.
- 최신 Claude 모델과 API에서는 temperature 같은 샘플링 값을 직접 바꾸는 대신, `effort`(생각의 깊이)와 프롬프트로 결과를 조절하는 방향으로 바뀌고 있다. 면접에서 "샘플링 파라미터를 어떻게 조절하나?"라는 질문을 받으면 이 변화도 함께 말할 수 있으면 좋다.

**확인 질문:**
- 분류나 정보 추출처럼 답이 하나여야 하는 작업에서 다양성을 높이면 생길 문제는?
- 같은 프롬프트로 평가(Eval)를 할 때 결과가 매번 조금 다르다면 어떻게 대응해야 할까? (4단계 예고)

## 5. 프롬프트 기법 (Prompting)

**비유:** 새로 온 유능한 동료에게 일을 맡기는 법. 배경, 목적, 기준, 예시를 주면 잘 하고, "알아서 해 줘"라고 하면 짐작으로 한다.

**정의:** 모델이 원하는 결과를 내도록 지시를 설계하는 일. 핵심 기법:
- **역할과 맥락:** 누구를 위해, 왜 하는 일인지 알려 준다.
- **명확한 기준:** 좋은 결과의 조건(길이, 형식, 포함할 것)을 적는다.
- **예시 (few-shot):** 원하는 입력과 출력의 짝을 몇 개 보여 준다.
- **구조화:** XML 태그나 마크다운 제목으로 지시와 자료를 구분한다.
- **구조화된 출력:** JSON 스키마를 지정해 정해진 형식으로만 답하게 한다.

**실제 사례:**
- 이 비서의 `prompts/persona.md`가 바로 시스템 프롬프트다. 사용자 정보, 말투, 규칙을 적어 두었다.
- `.claude/skills/*/SKILL.md`는 상황별 절차를 적은 프롬프트다. Skill은 필요할 때만 불러와 컨텍스트 윈도우를 아낀다.

**확인 질문:**
- 시스템 프롬프트와 Skill은 각각 언제 쓰는 게 좋은가?
- `persona.md`에서 하나를 고쳐 비서의 말투를 바꿔 보고, 무엇이 달라졌는지 적어 보자.
